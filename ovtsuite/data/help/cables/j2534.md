# J2534 devices and the OpenPort 2.0

CAN work — the ZF and Aisin transmissions, the Climatronic, the C6 cluster
and ABS, and the later EDC16 over CAN — needs a **J2534** pass-through
interface. The tested one is the **Tactrix OpenPort 2.0** (and its clones). A
J2534 device can also do K-line, where it does the init in hardware.

## The Tactrix OpenPort 2.0

The OpenPort 2.0 appears in the flasher's **Device** list (CAN) and, for
K-line, in the **Port** list marked **(J2534)**.

- **Windows:** install Tactrix's own J2534 driver. The OpenPort then shows up
  as a registered J2534 device.
- **Linux and macOS:** the app drives the OpenPort **directly over USB** — no
  vendor driver — and lists it as **(USB direct)**. This needs the **pyusb**
  package and the **libusb** library (see below).

The OpenPort can also do K-line, on its K-line pin; choose it on the K-line
transport.

## Registered J2534 devices (Windows)

On Windows, any installed J2534 device registers itself, and the app lists all
of them. A detail that trips people up is **bitness**: a J2534 driver DLL can
only be loaded by a program of the same bitness. The app shows each device's
bitness in its label.

- A 64-bit device loads directly.
- A **32-bit-only** device (the Scanmatik 2 PRO, for instance) is driven
  through a small 32-bit helper, and its label then reads **(via 32-bit
  bridge)**. The Windows installer includes that helper when a 32-bit Python
  was available at build time; if a 32-bit device is listed but cannot open,
  the message explains that the helper is missing. Installing a 32-bit Python
  so `py -3-32` works lets the app run the helper itself.

The bridge is only relevant on Windows; it never appears on Linux or macOS.

## Linux and macOS: OpenPort over USB

The direct-USB route needs:

- **pyusb** (a Python package), and
- **libusb-1.0** (a system library: on Linux the `libusb-1.0-0` package; on
  macOS, `brew install libusb`).

If either is missing, the **Device** list stays empty and says why, for
example *OpenPort: pyusb is not installed* or *libusb-1.0 not found*. The
installed Linux package already depends on libusb.

### Linux access

The installed package's udev rule (`70-ovtsuite.rules`) gives the logged-in
user the OpenPort without root or group membership, and tells **ModemManager**
to leave it alone — important, because the OpenPort enumerates as a serial
(CDC-ACM) device that ModemManager would otherwise probe and fight the app
for.

Running from source instead of the package, you do not get that rule. Then
install an equivalent udev rule for USB id `0403:cc4d` granting your user
access and setting `ID_MM_DEVICE_IGNORE=1`, or the OpenPort may not open. The
error when it cannot claim the device mentions checking the udev rule.

## Choosing between them

- On **Windows**, a registered J2534 device (OpenPort with Tactrix's driver,
  or another interface) is the normal route.
- On **Linux and macOS**, the OpenPort over USB is the route.
- For a later EDC16 over **K-line**, a J2534 device's hardware fast init is
  more reliable than a bit-banged KKL cable.
