# J2534 devices and the OpenPort 2.0

CAN work — the ZF and Aisin transmissions, the Climatronic, the C6 cluster
and ABS, and the later EDC16 over CAN — needs a **J2534** pass-through
interface. The tested one is the **Tactrix OpenPort 2.0** (and its clones). A
J2534 device can also do K-line, where it does the init in hardware.

## The Tactrix OpenPort 2.0

The OpenPort 2.0 appears in the flasher's **Device** list (CAN) and, for
K-line, in the **Port** list marked **(Direct-USB)**.

- **Windows:** install Tactrix's own J2534 driver. The OpenPort then shows up
  as a registered J2534 device. The app also ships **libusb**, so an OpenPort
  that has a **WinUSB** driver bound to it (for example with Zadig) is listed
  as **(Direct-USB)** too, with no vendor DLL. An OpenPort that is on
  Tactrix's driver is not listed that way: Windows allows one driver per
  device, so it is reached through the J2534 entry.
- **Linux and macOS:** the app drives the OpenPort **directly over USB** — no
  vendor driver — and lists it as **(Direct-USB)**. This needs the **pyusb**
  package and the **libusb** library (see below).

The OpenPort can also do K-line, on its K-line pin; choose it on the K-line
transport.

## The Scanmatik SM2 (Direct-USB)

On **Windows**, an SM2 that has a **WinUSB** driver bound to it is listed as
**(Direct-USB)**, in the **Device** list (CAN) and the K-line **Port** list, and
is driven without Scanmatik's DLL. Bind the driver with the installer's **Install OVT-Suite J2534 drivers** task or from
the Start menu entry **USB driver (OpenPort and SM2)** (**J2534 USB driver** when it
came from the separate add-on installer); it can put Scanmatik's own driver back. While Scanmatik's
driver is on the SM2, use its registered J2534 entry instead (Windows allows one
driver per device). Done and checked on a Scanmatik SM2 Pro: CAN (TP 2.0) and
K-line (slow and fast init). 29-bit CAN identifiers and parity other than none
are not available yet.

## Using the SM2 / OpenPort from other J2534 programs

With the **WinUSB** driver on the cable, the installer's **Install OVT-Suite J2534 drivers** task
also lists it as a J2534 device for other programs: one small DLL talks to the cable directly. Each
cable that is plugged in gets its own entry named after the model and its serial number
(**OVT-Suite SM2 (USB) 1234**, **OVT-Suite OpenPort 2.0 (USB) 5678**), so two cables of one kind stay
apart; a program that asks for the model name alone gets the first free cable of that model.
**Register J2534 drivers (OpenPort / SM2)** in the Start menu lists whichever cables are plugged in at
that moment (Windows asks for administrator permission; if anything fails, nothing is left
half-registered).

To register the drivers the DLLs are copied to a folder only an administrator can change
(`Common Files\OVT-Suite\J2534`), because the list of J2534 devices is machine-wide and a program
running as administrator loads them. **Deregister J2534 drivers** in the Start menu removes every
OVT-Suite entry (in both the 32-bit and the 64-bit registry view) and those copies; uninstalling
OVT-Suite does the same. If Windows' permission prompt is declined, or removal fails, the uninstaller
shows the command to run from an administrator Command Prompt:
`"%CommonProgramFiles%\OVT-Suite\J2534\ovtj2534cfg_x86.exe" unregister`.


## Registered J2534 devices (Windows)

On Windows, any installed J2534 device registers itself, and the app lists all
of them. A detail that trips people up is **bitness**: a J2534 driver DLL can
only be loaded by a program of the same bitness. The app shows each device's
bitness in its label.

- A 64-bit device loads directly.
- A **32-bit-only** device (the Scanmatik 2 PRO, for instance) is driven
  through a small 32-bit helper, and its label then reads **(via 32-bit
  bridge)**. The Windows installer includes that helper when a 32-bit Python
  was available at build time; if a 32-bit device is listed but cannot open,
  the message explains that the helper is missing. Installing a 32-bit Python
  so `py -3-32` works lets the app run the helper itself.

The bridge is only relevant on Windows; it never appears on Linux or macOS.

## Linux and macOS: OpenPort over USB

The direct-USB route needs:

- **pyusb** (a Python package), and
- **libusb-1.0** (a system library: on Linux the `libusb-1.0-0` package; on
  macOS, `brew install libusb` or `sudo port install libusb`; the app looks
  in `/opt/local/lib`, `/opt/homebrew/lib` and `/usr/local/lib`, and the
  `OVT_LIBUSB` environment variable can name the library or its folder).

If either is missing, the **Device** list stays empty and says why, for
example *OpenPort: pyusb is not installed* or *libusb-1.0 not found*. The
installed Linux package already depends on libusb.

### Linux access

The installed package's udev rule (`70-ovtsuite.rules`) gives the logged-in
user the OpenPort without root or group membership, and tells **ModemManager**
to leave it alone — important, because the OpenPort enumerates as a serial
(CDC-ACM) device that ModemManager would otherwise probe and fight the app
for.

Running from source instead of the package, you do not get that rule. Then
install an equivalent udev rule for USB id `0403:cc4d` granting your user
access and setting `ID_MM_DEVICE_IGNORE=1`, or the OpenPort may not open. The
error when it cannot claim the device mentions checking the udev rule.

## Choosing between them

- On **Windows**, a registered J2534 device (OpenPort with Tactrix's driver,
  or another interface) is the normal route.
- On **Linux and macOS**, the OpenPort over USB is the route.
- For a later EDC16 over **K-line**, a J2534 device's hardware fast init is
  more reliable than a bit-banged KKL cable.
